Time Complexity Algorithms

Learn how to analyze algorithm performance, understand how the number of operations grows with input size, and recognize common time complexity patterns.

Previous Next
Lesson Overview

How Efficient Is Your Algorithm?

Two algorithms may solve the same problem but perform very differently when the amount of data increases. Time Complexity helps us understand this difference by studying how the required computational work grows.

The Main Idea

Focus on Growth, Not Just Seconds

Instead of relying only on how many seconds a program takes on one computer, we examine how its computational work changes as the input gets larger.

Time Complexity describes the growth of computational work as input size increases. It is not an exact measurement of elapsed time in seconds.

Input Size

1. Understanding the Input Size

Before analyzing an algorithm, we need to identify the size of the input it processes. We commonly represent this size using the letter n.

Small Input

n = 10

An algorithm processes a small collection of elements.

Medium Input

n = 100

The algorithm may need to perform more operations to process the larger collection.

Large Input

n = 1,000

An efficient algorithm should handle increasing input sizes as effectively as possible.

The meaning of n depends on the problem. For an array, n might be the number of elements. For a string, it might be the number of characters.

Growth Rates

2. Common Time Complexity Classes

Different algorithms can have different growth rates. Understanding these common patterns makes it easier to compare solutions and recognize potential performance problems.

Excellent

O(1)

Constant Time

The operation count stays constant as n increases, assuming the operation itself has constant cost.

Example const first = numbers[0];
Very Efficient

O(log n)

Logarithmic Time

The search space is repeatedly reduced, as in Binary Search on a sorted array.

Example Binary Search
Scalable

O(n)

Linear Time

The work grows proportionally to the number of elements processed.

Example Visit every array element
Can Be Expensive

O(n²)

Quadratic Time

The work can grow quadratically when two loops each perform n iterations.

Example Compare every pair of elements

Why Does Growth Matter?

Consider these simplified operation counts.

Input Size O(1) O(log n) O(n) O(n²)
10 1 ~4 10 100
100 1 ~7 100 10,000
1,000 1 ~10 1,000 1,000,000

Illustrative growth counts, not exact runtime measurements. Logarithmic values are rounded for readability.

These classes are introduced here as common patterns. We will study how to express and analyze growth rates formally in the Big O Notation lesson.

Practical Example

3. Analyzing a Linear Algorithm — O(n)

Imagine that we want to display every number in an array. The algorithm must visit each element once.

printNumbers.js JavaScript 
function printNumbers(numbers) {
    for (
        let i = 0;
        i < numbers.length;
        i++
    ) {
        console.log(numbers[i]);
    }
}
01

Start at the First Element

The loop begins with index 0.

02

Visit Each Element

Each iteration processes one element and advances the index.

03

Stop at the End

The loop stops after reaching the array length.

Final Analysis

O(n) — Linear Time

If the input contains n elements, the loop processes n elements. Assuming constant work per iteration, its running time grows linearly.

Nested Loops

4. Analyzing Nested Loops — O(n²)

Now consider an algorithm that processes every possible pair of positions in a collection. Two nested loops can cause the number of operations to grow much faster.

printPairs.js JavaScript 
function printPairs(n) {
    for (let i = 0; i < n; i++) {

        for (let j = 0; j < n; j++) {
            console.log(i, j);
        }

    }
}
Outer Loop n iterations

The outer loop runs n times.

Inner Loop n iterations

For every outer iteration, the inner loop runs n times.

Total Iterations
n × n = n²

Therefore, this particular nested-loop pattern has quadratic time complexity: O(n²).

Nested loops do not automatically mean O(n²). Always analyze how many times each loop executes. If the inner loop runs a fixed number of times, for example, the overall complexity may still be O(n).

Performance Cases

5. Best, Average, and Worst Case

An algorithm's work may change depending on the particular input it receives. These cases describe different ways to analyze its performance.

Best Case

Most Favorable Input

The input that allows the algorithm to complete with the least amount of work for that input size.

Linear Search

The target is the first element.

Average Case

Expected Performance

The expected amount of work across inputs, according to a specified input distribution.

Linear Search

The target is at a typical position.

Worst Case

Maximum Work

The greatest amount of work the algorithm requires for inputs of a given size.

Linear Search

The target is last or is not present.

For a standard Linear Search, the best-case running time is O(1), while its worst-case running time is O(n). Average-case analysis depends on the assumptions about the input distribution.

Key Takeaways

What Should You Remember?

Use these ideas when analyzing algorithms and comparing different solutions to the same problem.

  • Time Complexity: Describes how computational work grows as input size increases.
  • Input Size: The variable n commonly represents the amount of input data.
  • O(1): Constant growth, assuming constant-cost operations.
  • O(n): A common pattern when processing every element once.
  • O(n²): A common pattern when two loops each perform n iterations.
  • Performance Cases: Best, average, and worst cases describe different input scenarios.
